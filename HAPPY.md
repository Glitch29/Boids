# Happy

Feedback about how the work goes: invocations, features and decisions that have regularly added
value in this project, and ones that have regularly subtracted it. Written from the side of the
conversation that sees every session — by the only participant who does.

**Status:** created 2026-08-30. **Staleness is not a defect here.** Unlike every other document in
this repository, an old entry is not a suspect entry, nothing needs keeping current, and there is
no date to check it against.

---

## The whole obligation

**Read it once, at the start of the session.** That is all of it. Nothing here is a permission, a
prohibition, or an instruction. Nothing needs to be acknowledged, actioned, quoted back, or
reported on, and an entry that does not bear on today's work costs nothing to pass over in
silence.

**The user writes this file. No session edits anything below this header** — not to add an
observation of its own, not to tidy, not to reformat. The value of the file is that it is one
person's voice, recorded across sessions that cannot see each other. An entry written by an
assistant would be that assistant grading its own work, which is the single perspective this file
exists to provide an outside check on.

## What kind of thing an entry is

Observations about *method* — how to go about a problem. Not findings about the simulation, which
belong in `HINTS.md`; not rules, which belong in `CLAUDE.md`; not state, which belongs in
`README.md`.

An entry is a prior, not a rule. It says what has tended to pay off here, so it should tip a
judgement call when nothing stronger is pushing the other way: reach for the approach that has
worked in this project before, rather than the one that comes to mind first. Where the situation
plainly calls for something else, do that — an entry is not a constraint and was never meant as
one. Where an entry and a hard rule in `CLAUDE.md` disagree, the rule wins.

When trying to determine the cause of missed identifications or classifications within a corpus,
analysis of a specific instance of failure has historically been more fruitful than trying to make
inferences from aggregated data.

When diagnosing an unknown issue with the user, proactively rendering some of the involved states
is often helpful. Especially when it would not require writing additional code to identify and
render those states.

The user puts significant effort into the avoidance of conflicting specifications. Sometimes the
user will make a mistake and you will identify a conflict. The user appreciates when these are
explicitly identified, and a mutual understanding about the amended specification is reached.

The user is good at geometrical inference. Sometimes passing the turn back to them with questions
is the best way to make progress on a problem.
